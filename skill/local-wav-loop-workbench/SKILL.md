# Local WAV loop workbench

Build an audio-preparation instrument whose exported bytes match its displayed frame accounting. The important work is explicit loop geometry, defensive RIFF parsing, and preventing delayed playback from starting after the user stopped or changed the selection.

## Scope and inputs

Begin with synthetic audio you generate. Reading a user's recording requires their selection/authorization; publication of the app does not authorize uploading recordings. A local-only design needs no microphone, account, remote codec service or analytics.

Choose supported formats explicitly. The worked build accepts mono/stereo little-endian RIFF/WAVE, PCM16/24/32 and IEEE float32 at 8–192 kHz, bounded to 25 MiB and five minutes. It rejects compressed and extensible WAVE rather than pretending to decode them. These limits are implementation choices.

References: [McGill WAVE format documentation](https://www-mmsp.ece.mcgill.ca/Documents/AudioFormats/WAVE/WAVE.html), [Web Audio looping](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode/loop).

## Build sequence

1. Implement the binary boundary first. Verify RIFF/WAVE identifiers and declared container bounds. Iterate chunks using declared sizes and odd-byte padding; do not assume audio begins at byte 44. Require usable format and data chunks, reject duplicate format/data chunks, and validate channel count, sample rate, block alignment, byte rate and complete frames before allocating sample arrays.
2. Decode supported numeric representations explicitly. PCM24 needs signed extension; float32 needs finite-value checks. Preserve sample rate and channels. Detect out-of-range floating samples rather than silently clipping them on import. Keep filenames and metadata out of generated exports unless the user requests them.
3. Express all edits in integer frames. Convert displayed seconds/milliseconds once, then show the actual rounded start, end, overlap and output frame counts. Treat the end as exclusive. Reject a blank field, reversed range, too-short selection, or an overlap at least half the selection. An overlap must be zero or at least two frames.
4. Define the overlap transformation before calling it a loop. For a selected length N and overlap F, emit the middle section from F through N−F−1, then F samples mixing the selected tail and head. For crossfade sample i, use t=i/(F−1), and mix tail×(1−t)+head×t. The result is N−F frames. At the cyclic boundary, the last sample is original head[F−1] and the first is original head[F], preserving their original adjacency. With F=0, copy the selection unchanged.
5. Explain the tradeoff. This constant-gain linear blend cannot exceed the input sample peak by summation alone, but it can attenuate correlated/opposing material and soften transients. It shortens the loop. An endpoint-jump metric is amplitude evidence, not a guarantee of perceptual seamlessness. Do not call arbitrary output click-free without listening.
6. Separate editing, monitoring and export gain. Optional peak scaling can target a stated level such as −1 dBFS; show that it changes the exported samples. Monitoring attenuation must not alter exported samples. Reduce monitoring gain further for out-of-range input. Block PCM export while samples exceed its range unless the user has applied an appropriate gain transformation.
7. Treat playback as cancellable asynchronous work. Create/resume AudioContext only after an explicit listen action. Increment a generation token on Stop, selection changes, clear and replacement. After awaiting resume, verify the token before creating a looping source. Stop and disconnect the old source and gain nodes. Stop on hidden-tab events. A late resume must never restart playback after Stop.
8. Apply the same generation rule to file reads. A delayed file import must not replace a newer demo or undo Clear. Preserve the last valid recording on an invalid import, but stop audio. Changed edit controls should stop playback and disable playback/export until rebuilt, avoiding stale output under new labels.
9. Render source and output envelopes with clearly labeled selection and channel. Include exact output duration, sample peak and overlap cost. Keep waveform decimation separate from audio processing: drawing fewer points must never change export samples.
10. Encode a new PCM16 WAV with correct RIFF length, sample rate, interleaving, alignment and data length. State any quantization, dithering or resampling behavior. Use a new filename; leave the source untouched. Verify generated bytes with an independent parser, not only the same decoder that created them.

## Worked verification

Seam Lab followed this workflow with an explicitly synthetic stereo tone. A three-second, 24 kHz recording with a 100 ms overlap produced 69,600 frames, exactly 2.9 seconds. Python's independent `wave` reader verified stereo PCM16, 24 kHz and that frame count.

Model tests covered PCM16 round-trip error within quantization, independent PCM24/PCM32/float32 fixtures, non-finite rejection, out-of-range detection, malformed RIFF bounds/alignment, exact overlap length/endpoints, zero-overlap copying and small-loop invariants across many lengths/fades. Simulated DOM/audio tests covered no autoplay, export bytes, listen/stop, dirty controls, invalid-selection recovery, canceled asynchronous resume, stale import versus Clear, hidden-tab stop and peak scaling.

Those tests passed for the worked implementation. Actual browser rendering, device playback and subjective audio quality were not verified. New implementations must run their own tests; a mocked AudioContext cannot establish how a speaker or browser sounds.

## Deliver

Provide the local app, a clearly synthetic sample WAV and the test evidence or concise results. State supported formats and remaining listening/browser checks. Publish only to the approved destination. In a skills-only repository, contribute the reusable workflow alone, keeping the product, sample audio and tests in the user's separate deliverable.
