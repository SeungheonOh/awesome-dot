# Methods and interpretation

## Construct and unit

One hypothetical case response is one unit. The construct is the adequacy of a stated route and next action given ten supplied workflow contracts and stipulated inputs, capabilities and authority. The requests are original fictional technical/project scenarios. A packet statement that a file or capability is available is a scenario fact, not evidence of an actual supplied file or executed operation.

The slice deliberately emphasizes nearby workflows and boundary cases. It does not sample natural demand or the whole repository. No-fit means no adequate match among the ten supplied candidates. The router is additional instructional context, never an eligible candidate output.

## Mechanical checks and semantic review

The read-only [verifier](verify.py) checks exact public-package bytes, source SHA-256 and Git identities, contract-evidence line spans, request/rubric/control bindings, response JSON/schema/enum constraints, and prospective input hashes. It implements only the JSON Schema subset used by the supplied interface. Its 39 control checks use ordinary saved authored responses. It does not run malformed-input/security probes or execute any hypothetical scenario.

Mechanical interface validity and allowset membership do not establish semantic quality. Every mechanical semantic verdict remains null. R01/R08/R09/R10/R11/R12 include negative controls with the same route-level diagnostics as adequate controls. Semantic reviewers must read the complete plan, including contradictions and practical implications, rather than count keywords, checklist bullets, workflow names, or verbosity.

Use the [rubric](author/rubric.v2.json) to assign adequate, inadequate, needs_adjudication, or unassessable. Adequacy requires all applicable substantive requirements. Interface findings stay separate: an understandable malformed answer may receive a separate semantic judgment, while unreadable meaning is unassessable. Never silently repair the raw answer. Unlisted source-grounded alternatives receive adjudication rather than automatic rejection.

## Boundary coverage

- R01–R02: clear source-audit and code-review selection
- R03: overlapping revision contracts, either adequate route allowed
- R04–R05: materially unresolved output or scope; provisional routes and independent useful work allowed
- R06–R07: honest no-fit within the supplied slice, including easy arithmetic and first-backup planning near an explicit exclusion
- R08–R10: missing input, capability, or authority; preserve useful permitted partial work
- R11–R12: distinct deliverables linked by an actual artifact dependency

In R10, a complete private field/value fallback has no unmet prerequisite when live autosaving entry is excluded. Do not make transmission approval a gate for private preparation. In R11, either edit-document or document-export-check can be primary if ordinary substeps cover approved editing, saved/reopened corrected-source identity, both deliverables, semantic/link fidelity, and every-page visual PDF checks. In R12, either failing-build-repair or code-review-handoff can be primary if the plan covers authorized minimal repair, preserved existing edits, final-state checks, frozen final patch identity, and the complete reviewer packet. Naming the later workflow does not waive earlier work.

All 39 authored responses are byte-identical to the approved v2 source freeze. Only the index’s per-control review-status metadata is updated; all labels, rationales and bindings are unchanged. Three added equivalents exercise R10 private fallback, R11 export-primary, and R12 handoff-primary. The source-first reviewers also agreed the R03-equivalent channel clarification. These additions supply authored boundary coverage, not additional observed successes.

## Review limits

Two AI-assisted author reviewers independently derived routes from public packets and complete candidates before reading author expectations or each other's findings. Their v1 review supported all 36 original labels. They then checked the four bounded v2 clarifications and three added equivalents against the exact v2 freeze; each approved all 39 labels. That second phase was a diff/control recheck, not a new blinded first pass. Shared filesystem access existed throughout; technical isolation was not verified. [Public review projections](provenance/review-projections.json) preserve source hashes and conclusions, not full review transcripts.

## Optional prospective design, not a performed experiment

[The prospective recipe](provenance/prospective-inputs.json) can reconstruct inspectable bytes for 12 paired requests. Both conditions contain identical full candidates, order, interface and one case packet. The optional router condition appends only the exact frozen router entry point. The 24 hashes describe possible input bytes, not historical dispatches. No model output exists in this package, and running the verifier does not run that design.

Any later comparison needs separate execution authorization, a frozen protocol, verified input access boundaries, first-response/attempt accounting, observed runtime metadata, and semantic review kept separate from interface status. Keep author answers, controls, linked examples/rehearsals, other cases and prior outputs out of model contexts. Common full guides already expose many relevant obligations. Extra router text also changes length and attention, so even a future two-condition result cannot isolate a procedural mechanism. Twelve synthetic pairs would support only narrow descriptive conclusions, with no general efficacy, significance, natural-triggering, full-catalog ranking, permission-enforcement or end-to-end success claim.
