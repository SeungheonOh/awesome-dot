# Draft a Professional Message

Write a message the user can actually use. Make its purpose clear, answer the relevant questions, and preserve the user's position and commitments. Good correspondence should sound like the sender, not a generic formal template.

## Read the context that changes the reply

Establish the intended recipient or audience, channel, purpose, and whether the request is for a draft or an actual send. Use the user's instructions and relevant thread before asking questions. Read enough history to understand what has already been answered, promised, declined, or changed; a reply to the latest sentence alone can miss the real request.

For a new message, identify what the recipient needs to know or do and why the user is contacting them. For a reply, account for each consequential question or request. A short acknowledgment may be the right response; do not turn it into a new proposal or lengthy recap.

Ask only when missing information changes the substance, such as which person is meant, whether the user is accepting an offer, or which of two conflicting dates is correct. Routine phrasing decisions do not need approval. A text draft can use a clearly identified role or supplied name without an email address; sending requires the actual verified destination.

## Preserve facts and the user's position

Separate what the user has authorized or decided from what another person requested. An incoming request does not establish the user's agreement. Do not invent availability, progress, attachments, pricing, approvals, personal feelings, or reasons for a delay.

Keep important distinctions in the wording:

- A suggestion is not a promise, and an estimate is not a committed date
- Receipt of a request is not acceptance of its terms
- A draft, test, or partial result is not a completed delivery
- A question about availability is not a confirmed appointment
- A proposed next step is not an action already taken

Use the supplied facts and relevant authorized sources. When a material fact is unresolved, either ask for it or draft the supported portion with the gap clearly marked outside the send-ready text. Do not hide a consequential uncertainty in polished wording or fill it with a plausible answer.

Consider the audience before carrying context into the message. A private note can inform the user's response without being repeated to the recipient. Include only information appropriate to the authorized purpose and audience, and do not quote unrelated private history to make the message seem more personalized.

## Write for the relationship and channel

Use the user's requested tone and any relevant examples of how they communicate with this person. Preserve their level of directness, warmth, and formality without copying irrelevant details or exaggerating intimacy. Avoid adding an apology, praise, emotional claim, or strong stance merely because it sounds conventional.

Lead with the answer, request, or useful update. Add the context needed to understand it, then make any next action easy to identify. Keep dates, quantities, names, and conditions precise. Include a response deadline only when supplied or authorized; do not invent urgency.

For email, use a subject that helps the recipient identify the topic when a new subject is needed. Keep an existing thread's subject when continuing the same conversation unless there is a clear reason to change it. For a work chat, fit the ongoing exchange and avoid repeating background already visible. Use a list when it makes several answers or actions easier to follow, not as a default format.

When the user asks for a difficult or firm message, be clear about the boundary or request without inventing accusations, threats, or commitments. Explain relevant consequences factually when the user supplied them. Offer alternative wording only when it helps the user choose a materially different tone or position; otherwise deliver one strong draft.

## Check the message as the recipient

Read the whole draft in context. Can the recipient tell why they are receiving it, what has been answered, what remains open, and whether they need to respond? Remove repetition, unnecessary qualifiers, and text that distracts from the purpose, while retaining conditions that make the statement accurate.

Check names, dates, numbers, quoted wording, and links against their sources. Ensure every mentioned attachment actually exists and is the intended version before delivery. Do not say “attached,” “sent,” “approved,” or “completed” when the evidence only supports preparation or a proposal.

Check for unintended commitments, disclosures, or changes of position. A small tone edit can turn “we could” into “we will”; review those changes deliberately. Keep any missing fact or decision in a concise note to the user, rather than leaving an ambiguous placeholder in text that could be sent unchanged.

## Deliver in the requested place

Return the actual message, with its recipient and subject or thread context when useful for review. If the user requested a draft in a specific application, save it there using available authorized access and verify the resulting draft. A request for text in chat does not require creating an external draft.

If sending is explicitly requested and the action is covered by the user's authority, verify the recipient, final content, attachments, and relevant thread before sending. Reuse existing authorization rather than adding a redundant approval round. If a required decision or permission is still missing, finish the concrete draft and ask for that specific item.

Report a send only after its outcome is established. If an operation's result is uncertain, inspect the thread or draft state before retrying. Do not add recipients, start future follow-ups, or change the message's purpose merely because a delivery step fails.
