# Orbit Slingshot Physics Game

Build a deterministic launch-and-observe game with adjustable trajectories and a readable physics model.

## Scenario

A science museum volunteer wants visitors to learn by adjusting a launch rather than memorizing equations. A fictional space course makes trajectory changes visible. The game should pause freely, show why a probe missed, and reproduce the same flight when the same launch settings are entered.

## Inputs to prepare

- [COURSE COUNT] and target difficulty
- [LAUNCH SPEED RANGE] and angle controls
- [GRAVITY MODEL] chosen from simplified options
- [ACCESSIBILITY OPTIONS] and screen-size priorities

## Copy this prompt into dot

```text
dot, help me build Orbit Slingshot, a browser game about launching a probe through a fictional gravity field. Use [COURSE COUNT], [LAUNCH SPEED RANGE], [GRAVITY MODEL], and [ACCESSIBILITY OPTIONS]. If coding and browser execution are available, first make one course with numeric angle and speed controls; otherwise deliver the design and implementation plan without claiming a playable build.

The player predicts a trajectory, launches, then watches or steps through the flight. Passing through the target zone with the stated speed condition wins. Hitting an obstacle, leaving the bounded playfield, or reaching a fixed simulation-step limit fails with a clear reason. Use a fixed timestep and document the simplified force equation, collision rule, units, and numerical limits. This is an educational toy, not orbital navigation software.

Include pause, single-step, trajectory trail, retry with the same settings, and reset to the course defaults. Offer keyboard controls, readable numeric values, reduced motion, and no time pressure while aiming. Deliver source, course data, a few reproducible winning launch settings, and test notes. Check near-zero distances, extreme allowed speeds, collisions between frames, and identical seeded replays. Keep previews private and ask before publishing or collecting scores. Clearly mark any physics or browser checks not actually executed.
```

## Iterate with a purpose

### 1. Compare trajectory predictions

```text
Add an optional predicted path generated by the same integration rules and compare it with the actual replay at every recorded step.
```

### 2. Create a course editor

```text
Add a local course editor with bounded masses, nonoverlapping start zones, and exportable course JSON.
```

### 3. Teach numerical error

```text
Add a separate experiment comparing two timesteps on the same launch, explaining differences without changing the main game rules.
```

## Expected deliverables

- Editable game source and physics-model note
- Course files and reproducible winning launch settings
- Keyboard and pause-control guide
- Determinism, collision, and numerical-edge-case checklist

## Acceptance checks

- A supplied winning launch reaches its target under the documented speed condition
- Obstacle, boundary, and step-limit failures each show a distinct cause
- Retry with identical inputs reproduces the same recorded trajectory
- Pause leaves simulation time and probe position unchanged
- Near-zero separation is bounded without NaN or infinite coordinates
- Maximum permitted speed cannot pass through an obstacle undetected
- Reset removes trails and restores launch settings and game outcome

## Access, privacy and stop conditions

- The simplified force model is unsuitable for real flight or engineering
- Reproducibility is bounded by the documented runtime and numeric implementation
- Code execution, private preview, and browser validation depend on available tools
- Publication and score collection require approval

## Two possible extensions

- Create a printable launch-prediction worksheet
- Add a side-by-side comparison of two saved local trajectories
