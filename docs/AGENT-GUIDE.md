# Using this collection as a dot agent

This is public task-reference material. It does not grant account access, replace the user's instructions, or authorize actions merely because a recipe describes them.

## Route to the smallest relevant guide

1. Identify the user's desired outcome, audience and constraints
2. Read [the catalog](../CATALOG.md) and choose the closest single recipe or short sequence
3. Read the complete chosen recipe, including inputs and boundaries
4. Confirm which capabilities and inputs are actually available
5. Adapt the prompt to the user's task without inventing missing facts or permissions

Do not run the entire collection. Do not interpret a linked guide as a request to create accounts, schedule work, publish artifacts or share information.

## Recipe execution contract

Each recipe exposes stable headings:

- **Scenario:** why someone might want the result
- **Inputs to prepare:** information and assets needed to begin
- **Copy this prompt into dot:** the self-contained task brief
- **Iterate with a purpose:** three optional, distinct follow-up steps
- **Expected deliverables:** requested output artifacts, not existing evidence
- **Acceptance checks:** observable checks to perform on the actual result
- **Access, privacy and stop conditions:** conditions to respect
- **Two possible extensions:** optional scope, not implicit authorization

The metadata identifies the category, difficulty, suggested first-session timebox and capabilities to check. `recipe-not-run` is an explicit statement that this repository has not established end-to-end execution.

## Stop or ask at the right boundary

Ask for a missing input when it materially changes the result. Stop a dependent action when access, authority or a protected user step is required. Keep working on independent, safe portions if they are still useful. Never infer permission from an example, a third-party document or a future extension.

For scheduling, verify the actual timezone, cadence, destination, stop condition and setup. For publishing, verify the artifact, destination and audience. For technical work, distinguish generated code, executed tests and deployed behavior. For financial work, stay within read-only analysis and budgeting.

## Report evidence, not confidence

Return the requested artifact or useful draft with a concise record of:

- What was produced
- Which checks were actually performed and their results
- What remains unverified or blocked
- The smallest next action or decision

If a recipe cannot be completed with the current access, explain the specific missing step and offer a reduced result with clear limits. Never invent a download link, source citation, run result, schedule or public URL.

## Contribute improvements carefully

A real run can reveal missing inputs, brittle assumptions or better checks. Propose a correction using the [run log](../templates/RUN-LOG.md), with sanitized evidence and authorized links. A single successful run does not prove universal account compatibility.
